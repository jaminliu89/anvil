# Group Board Review — Anvil

Date: 2026-09-05
Decision: **RESCUE, DO NOT EXPAND**

## CEO / Strategy

Anvil remains strategically useful only if it becomes a simple control surface for getting real Agent work done. The company does not need another impressive architecture demo. It needs an owned execution/control capability that can later serve multiple products.

Decision: keep Anvil; do not create a replacement repository or rename it during rescue.

## CPO / Product

The current product fails the primary-user test because the founder does not know how to use it. The rescue product promise is therefore reduced to one buying/use moment:

> I have a repository and a task. I open Anvil, say what I want done, watch it work, inspect the result, and decide whether to accept it.

Everything that does not improve this moment is LATER.

## PM

Only Vertical Slice 001 is NOW:

1. Launch Anvil reliably.
2. Choose repository through UI.
3. Enter task in plain language.
4. Run.
5. See plan/execution/status.
6. Approve when required.
7. Receive test/result/diff.
8. Accept or reject.

Acceptance = Kim Test, not developer demonstration.

## CTO / CTAB

Approve Tauri 2 + Vue 3 + TypeScript and salvage the existing UI shell. Build the smallest owned task/runtime contract. Dock remains a replaceable coding worker. Remove experimental model/harness/training dependencies from the critical startup path.

## COO / Execution

No parallel feature branches for new capabilities until VS-001 passes machine verification. Agent work must be issued from the frozen Change Contract. Progress is measured by runnable evidence, not commits or lines of code.

## CFO / Capital efficiency

The rescue path maximizes reuse of existing Anvil and Dock assets and avoids another repository/framework migration. No paid infrastructure or persistent cloud services are justified for Phase 0. Local-first remains the default.

## Investor view

The defensible asset is not a desktop wrapper around other companies' agents. It is the owned contract, task lifecycle, execution governance, evaluation data and cross-product runtime capability accumulated over time. External harnesses are research accelerators, not the moat.

## Asset Governance

- Anvil: SALVAGE / selectively REWRITE.
- Dock: KEEP / freshly VERIFY.
- Existing multi-adapter integrations: QUARANTINE until individually justified.
- DSH bridge: remove from critical path; retain only as research/optional adapter asset.
- Training surfaces: LATER.
- Existing UI components: reuse only when they support VS-001.

## Brand / Packaging

Keep **Anvil** and **Dock**. No OS suffix and no temporary engineering name promoted to product brand. Naming/packaging work resumes only when the product has an ACCEPTED core behavior worth packaging.

## Board kill criteria

Pause or reconsider Anvil if, after the constrained rescue implementation:

- it still cannot pass Kim Test;
- the simplest real task requires users to understand internal adapter/harness commands;
- Dock cannot be made reliable behind a narrow worker contract without disproportionate repair;
- a fresh asset audit proves salvage cost exceeds a minimal clean implementation behind the same Anvil contract.

## Board resolution

**Proceed with VS-001 implementation under CTAB constraints. No feature expansion. No new runtime repository. No new brand.**
