# Anvil Rescue Audit

Status: **FAILED / NOT USABLE**

This status is intentionally product-level, not a judgment that every existing code asset is worthless. The founder currently cannot reliably launch Anvil and complete a real task without developer/Agent assistance; therefore Anvil is not accepted as an MVP.

## Governing rule

Anvil follows the group Product Governance Layer and Capability Ledger lifecycle:

`PLANNED -> IMPLEMENTED -> VERIFIED -> ACCEPTED`

README claims, code presence, screenshots, architecture diagrams, unit tests, or Agent self-reports do not equal ACCEPTED.

## Rescue objective

Do not add features. Restore one usable vertical slice:

`Launch -> create real task -> execute -> observe status -> inspect result -> accept`

For the first coding slice:

`Anvil -> task/session -> runtime boundary -> Dock/coding worker -> worktree -> coding agent -> test -> result/events -> Anvil timeline`

## Founder acceptance / Kim Test

Target: founder completes the core flow within 10 minutes through normal product entry, without a development Agent explaining hidden steps or editing source code.

Until this passes, product status remains FAILED / NOT USABLE.

## Immediate non-goals

- No new model/provider integrations.
- No training platform expansion.
- No benchmark/evolution engine implementation yet.
- No new desktop surfaces unrelated to the vertical slice.
- No copying/forking DeepSeek Harness, Codex, PenguinHarness, or another runtime as Anvil's core.
- No new repository unless Board + CTAB + Asset Governance conclude existing assets cannot support the target architecture.

## External research policy

DeepSeek Harness, Codex and PenguinHarness are reference assets only. Study capabilities, trade-offs, benchmarks and public architectural principles; Anvil contracts and implementation remain independently designed. Keep provenance/licensing records even where no external code is copied.

## Audit classification

Every existing capability/code path must be marked one of:

- KEEP — working, aligned asset.
- SALVAGE — valuable concept/code but not currently usable.
- QUARANTINE — unverified or risky; cannot participate in accepted path.
- REMOVE — duplicate, dead, misleading or harmful.
- REWRITE — requirement remains but implementation should be replaced behind a frozen contract.

## Exit criteria for Rescue Phase 0

1. Capability Ledger reflects reality.
2. README current-capability claims no longer outrun ACCEPTED evidence.
3. Board / CTAB / Asset Governance decision is recorded.
4. Runtime dependency direction and contracts are frozen before feature implementation.
5. One vertical slice is specified with executable acceptance evidence requirements.
